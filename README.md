# 售后返件登记系统

面向 CQE 售后返件业务的登记与统计程序。数据存储在本机 MySQL 8
（六个 schema），不依赖外网。

**2026-09-20 三处架构变更**（为服务器部署做准备）：

| 变更 | 说明 |
|---|---|
| 数据接口方向 | 本系统**不主动推数据**，由**外部系统的定时任务来拉取**；开放独立端口的取数接口（令牌 + IP 白名单），需要时在防火墙单独放行 |
| 金山同步模块移除 | 2026-09-21：金山文档同步模块（`sync_log` 表、`sync_state` / `synced_at` 字段、金山侧目标配置）**整体删除**；对外数据接口保留，供任意外部系统拉取 |
| 登录验证 | 默认开启；权限模型是「权限组 + 权限点」两级，预置 管理员 / 登记员 / 只读，可自定义 |
| 部署预留 | 监听地址、公开地址、Cookie 安全项全部支持环境变量注入，`deploy/` 下备好 Nginx 与 systemd 样例 |

**2026-09-22 数据库换成 MySQL 8**：

| 变更 | 说明 |
|---|---|
| 引擎 | 六个库从「`data/*.db` + SQLite `ATTACH`」改为「六个 MySQL **schema** + 一个连接」。schema 名与旧文件名一一对应（`returns.db` → `returns_db`） |
| 为什么换 | 集中备份与恢复（`mysqldump` 文本快照 + 影子库还原演练，见「数据与备份」），以及摆脱单机文件锁 |
| 影响面 | 只动数据层：`core/db.py`（连接 / DDL）+ 六个 `core/repo_*.py` 的 SQL 方言。**`app.py` 与前端一行没改** |
| 依赖 | 新增 `PyMySQL`（数据层驱动）与 `pymssql`（ERP 取数，仍是可选） |
| 本机 | `python tools/dev_mysql.py start` 起一个免安装的 MySQL 8.0.29（口令在 `.workbuddy/binaries/mysql/credentials.json`）；`env`/`ARS_MYSQL_*` 亦可连外部库。⚠️ 这份是**免安装的裸进程**、没有服务守护：它若退出（Windows 上被安全软件/进程回收静默收掉时 `mysqld.err` 里连 shutdown 都不会有），用 `status` 看、`start` 拉起来即可 —— 应用侧会自己重连（见「常见问题」） |
| 备份 | `tools/backup.py` 改走 `mysqldump --single-transaction`；`tools/check_backup.py` 从「校验 sha256」升级为**真的还原到 `verify_*` 影子库逐表比行数** |

> 迁移脚本 `tools/migrate_sqlite_to_mysql.py` 把旧 `.db` 里的数据搬进六个 schema
> （一次性，幂等）。旧 `.db` 文件保留在 `data/` 下不动，作为回退底稿。

## 快速开始

**前置条件：MySQL 8 已在跑。** 数据不再放在 `data/*.db` 里，起服务前先确认库能连上。

```bat
:: Windows —— 首次使用：初始化环境（创建 .venv 并安装依赖）
setup_env.bat

:: 本机没有 MySQL 的话，用免安装版一键装好并起库（建六个 schema + ars 账号）
python tools\dev_mysql.py setup

:: 日常使用：启动服务
start.bat
```

```bash
# Linux / macOS —— 同上
./setup_env.sh
# 库由系统包管理器装（apt install mysql-server / dnf install mysql-server），
# 或用任何外部 MySQL：把 ARS_MYSQL_HOST / _PORT / _USER / _PASSWORD 指过去
./start.sh
```

> `python tools/dev_mysql.py status` 看库在不在跑；`start` / `stop` 启停它。
> 连接信息存在 `data/mysql.json`（口令文件，已被 `.gitignore` 排除），
> 环境变量 `ARS_MYSQL_*` 优先级更高。

启动后访问 **http://127.0.0.1:8000**（仅本机），用 **`admin` / `admin123`** 登录
（首次登录会强制改密）。

启动横幅会打印实际连的库，用来确认没连错环境：

```
 数据库      mysql://ars@127.0.0.1:3306
```

服务会同时拉起**两个端口**：

```
主界面     http://127.0.0.1:8000     ← 人用，需登录
数据接口   http://127.0.0.1:8100     ← 外部系统定时拉取用，需令牌
                                      （默认也只监听本机）
```

> **要开放访问**（局域网 / 公网），不必改代码，用启动参数或环境变量。
> Windows 的 `start.bat` 与 Linux/macOS 的 `start.sh` **三档预设完全一致**：
>
> | 命令 | 主界面 `:8000` | 数据接口 `:8100` |
> |---|---|---|
> | `start.bat` | `127.0.0.1` | `127.0.0.1` |
> | `start.bat --lan` | `0.0.0.0` | `127.0.0.1` |
> | `start.bat --public` | `0.0.0.0` | `0.0.0.0` |
> | `start.bat --local` | 强制 `127.0.0.1` | 不变 |
>
> ```bat
> set ARS_HOST=0.0.0.0 && start.bat   :: 等价于 --lan，且可覆盖任意配置项
> start.bat 0.0.0.0 9000              :: 直接指定 host / port
> ```
>
> **优先级：环境变量 > `--lan` / `--public` 预设**（你自己设的 `ARS_HOST`
> 是刻意的，不被预设覆盖）；`--local` 是例外，它强制本机。
>
> 两个地址是**独立**的：只改主界面不会让数据接口对外，反之亦然。
> 启动时会打印实际监听到哪、以及本次的可达范围。首次开放时若系统弹
> 防火墙提示，选择「允许访问」。**开放前请先改掉初始管理员密码**，
> 公网还须按 `--public` 打印的四项检查（改密 / 重置令牌 / IP 白名单 / HTTPS）。

### 退回登记：多行明细录入

页面顶部是**自动匹配栏**，往下分「整单信息」与「产品明细」两块：

- **自动匹配栏**（页面唯一的扫码入口，2026-09-20 新增）：扫进来的条码按两种格式分流 ——

  | 扫进来的内容 | 做什么 |
  |---|---|
  | `料号\|产品编号`（例 `10006-0021\|231006937`） | **拆分**：左段进「料号」、右段进「产品编号」，并照旧自动补全型号 / 规格 / 品名 / 类别与生产年月 |
  | **快递单号**（历史里有过） | 回填整单信息（含历史带出的风机厂家 / 项目风场 / 快递公司） |
  | 料号 / 产品编号 / 售后单号（历史里有过） | 新增一行并回填 |
  | **历史里查不到的条码** | **不猜** —— 提示框里给出两个按钮「当快递单号」/「当产品」，点一下决定它的去向 |

  > **为什么要问**：快递单号与产品编号都可能长得像纯数字（快递单号多为 12~15 位、
  > 产品编号 8~9 位，还有 `SF…` 这种带字母的），机器猜错就会把数据归到错的地方
  > （单号跑进产品编号，或产品编号跑进退回单号）。所以这一种情况交回给人判断，
  > 只多一次点击；**同一个条码再扫仍会问**，不擅自沿用上次的选择。

  扫完**自动清空输入框、光标留在栏内**，可以连着扫；结果写在栏下那行状态里
  （绿=正常、黄=需留意）。**「退回单号」已有值时不会被新扫的单号覆盖** ——
  只提示「未覆盖」，要换单请先清空该栏（否则两个快递单会被合并到同一条记录下）。
  扫快递单号后**不会**往明细里塞空行，光标留在栏里，方便接着扫产品。

  > 焦点不在输入框时，全局扫码枪走的是**同一个入口** —— 所以不论光标在哪，
  > 上面两种格式都能正确分流。「清空重填」后光标也落在这一栏。

- **整单信息**（7 项，填一次即作用于该快递单下全部明细行）：
  退回单号、快递公司、退回时间、售后单号、风机厂家、项目风场、快递归属。

  > **退回时间**与**售后单号**均为锁定只读：退回时间固定为当天；
  > 售后单号由系统按快递单号自动判定，不接受手工填写（见下文「补登与查重」）。
- **产品明细**是可增删的表格，**一行一只产品**，11 列：
  产品编号、料号、产品型号、产品类别、品名、规格、生产年份、
  生产月份、退回数量、反馈现象、分析报告。支持三种录入方式：
  1. 扫产品条码 —— **自动新增一行**并回填匹配到的产品信息；
  2. 点「＋ 新增一行」手工填写；
  3. 从 Excel 复制多行，在表格中直接 `Ctrl+V` 粘贴，按当前列顺序自动拆行。
  4. **回车 = 换行**：在**最后一行**的任意格按回车，自动新增一行，光标停在新行的
     同一格（可连续录入）；在**中间行**按回车则焦点下移到下一行的同一格，
     便于逐行核对。料号 / 产品编号格的回车仍**先**完成回填 / 生产年月解析，再换行。

     > 用键盘在候选面板里回车**选中候选**的那次只算「选中」，不会顺手开新行
     > （否则挑候选就会多出一行）；选中后再按一次回车即换行。
     >
     > 换行后光标落到新行的格子**不会自动弹开候选面板** —— 只有你点击该格或
     > 手动敲字时才弹，免得连扫时面板一直闪。

- **料号自动回填**：在任意一行的「料号」栏输入（或扫码枪扫入）料号并回车，
  系统会立即从**匹配数据库**带出该产品的固有属性：

  | 填入列 | 取自匹配数据库 |
  |---|---|
  | 产品型号 / 规格 | `spec`（规格号，如 `51177.67.773C`） |
  | 品名 | `product_name` |
  | 产品类别 | `production_stat` ← **类别信息存在这一列**，`category` 列是空的 |

  输入规格号（如 `51228.68.242`）同样能反查命中；匹配库没有该码时，
  会退回**返件历史记录**或**型号字典**兜底，并在提示区说明来源。

  **生产年份 / 生产月份刻意不自动填** —— 匹配库没有这两个字段，而历史同规格
  记录的年份跨批次并不一致（实测最多 6 种取值），自动填入等于凭空造一个
  看似可信的错值，不如留空照铭牌填。

  两条保护规则：
  - **人工优先** —— 只填空格，或覆盖上一次由系统自动填入的值；你手改过的格
    永不被后续自动逻辑改写；
  - **未命中会回退** —— 料号查不到时标黄提示，并清掉上一轮由系统填入的值
    （人工填的保留），避免错误的自动值留下来误导。

  从 Excel 粘贴多行料号时，粘贴完成会自动**逐行补全**并显示进度。

### 明细行的模糊匹配（与检测登记同一套交互）

明细行里凡是「输入型」的格都是**可搜索下拉** —— 输入关键字即弹出候选，
选一个即可，也可直接录入新值：

| 字段 | 候选来源 |
|---|---|
| **料号** | **匹配数据库**（1735 条物料主档）—— 按 料号 / 旧料号 / 规格 / 型号 / 品名 模糊匹配，料号前缀命中的排最前，候选带「品名 · 型号」副标题便于分辨 |
| **产品编号** | **不设候选**（2026-09-20 起改为纯输入框）—— 铭牌序列号是一次性的，模糊候选只会干扰，还可能误选到别的序列号 |
| **生产年份 / 生产月份** | 同上（便于手工修正时不再手敲） |
| 产品型号 / 产品类别 / 品名 / 规格 / 反馈现象 | 字段字典（历史累积，带使用次数）|

举例：料号格输入 `10002` → 列出 `10002-0001 抗冰冻风速传感器 · BLF1-SII` …
选中后**照旧自动回填**产品属性，与回车触发完全一致。

**扫码枪自动识别**：连续极快输入（字符间隔 < 35ms）视为扫码，全程不弹候选面板 ——
否则面板会闪、回车还可能被面板抢去变成「选中第一项」，而扫码后应当触发自动回填。

> 接口：`GET /api/items/search?kw=&limit=`（匹配库候选）、
> `GET /api/dict/{field}?keyword=`（任意字段的历史值去重检索）；
> 前端由 `common.js` 的 `fetchCandidates(f, kw)` 按字段的 `source` 统一分派。

- **生产年月自动识别**：**产品编号前 4 位就是生产年月（YYMM）**，
  在「产品编号」栏输入或扫入后回车即可自动填出：

  ```
  产品编号  20100341
            └┬─┘
            YYMM   →  YY=20 → 2020 年    MM=10 → 10月
  ```

  解析不出来时（编号带字母、月份越界）写 **「无法确认」** 而不是留空 ——
  让「还没查」和「查了但编号不规范」在数据上可区分，
  后续可在明细查询页筛出来人工修正。产品编号为空则不填（没有依据）。

  同样受「人工优先」保护：你手改过的年月不会被后续解析覆盖。

  逐字符校验 ASCII 数字，月份限定 01–12，年份上限取「明年」以容忍跨年生产 ——
  像 `2013`（月 13）、`240055905`（月 00）、`105F-7FDB`（含字母）、
  `991200001`（99xx 不合理）都会落到「无法确认」。

> 备注与登记人不在登记页出现。登记人由系统自动记为默认值，
> 备注可在「明细查询」页打开记录后补录。

> **退回登记只填「收到产品后初步能确定」的内容。** 凡是要拆包检测才能判定的
> 字段（检测时间、检测结果、故障原因、改善措施、处理方案、问题分类、责任归属、
> 完结状况、报告编号、ERP处理、照片证据）一律移到了**检测登记**模块，
> 见下文「检测登记」一节。

提交前底部会实时显示「本次将提交 N 条明细，行号在所选售后单号下自动递增」。

扫到**快递单号**时不会新增行，而是回填整单信息（退回单号、厂家、风场、快递归属等），
方便先扫单号再逐件扫产品。

### 检测登记

送检后录入检测结果的工作台。**清单按售后单聚合（一单一行），录入按明细行进行**：

```
扫码定位 ─┐
          ├─→  待检清单（按售后单聚合，一单一行）  ─→  点选某单
列表筛选 ─┘                                              ↓
                              右侧列出该单全部明细行  ─→  点选某行  ─→  录入  ─→  保存
```

| 分区 | 字段 |
|---|---|
| **检测信息** | 检测时间（锁定）、检测结果、故障原因、改善措施、处理方案 |
| **归因与结论** | 问题分类、责任归属、完结状况（自动）、报告编号、ERP处理、**照片证据（图片上传）** |

**完结状况为自动判定**，不接受手工填写（界面上只读）：

```
以下 7 项检测字段全部有值  →  已完结
（检测时间 · 检测结果 · 故障原因 · 改善措施 · 处理方案 · 问题分类 · 责任归属）
任一项为空  →  未完结（存空值）
```

> **「有值」= 非空字符串**，所以 `/` 这类占位符也算已填（那是金山侧人工填的
> 「本栏不适用、已确认过」，与"没填"是两回事）。历史导入时有三列已把 `/`
> 换成更准确的词：**故障原因 → NTF**、**改善措施 → 暂无改善**、
> **处理方案 → 拆解报废**（见「从金山文档导入历史数据」）。
>
> **读取端把空值归一为「未完结」**（`config.INSPECT_DEFAULT_VALUES`，机制与
> `HANDLE_DEFAULT_VALUES` 相同），所以界面上**只会看到「已完结 / 未完结」两种**，
> 明细查询的筛选下拉也是这两项（`FIXED_OPTIONS['completion']`）。
> ⚠️ 但**存储层不变**：未完结仍存空值，SQL 里判完成度必须继续用**裸列**
> `completion NOT LIKE '%完结%'` —— 归一转出来的「未完结」**含「完结」二字**，
> 拿它去 LIKE 会把未完结全算成已完结。同理前端判完结要用**严格等**，
> 不许用 `includes` 找子串（`check_frontend.js` 有断言守着）。

**不参与判定的三个字段**（`config.COMPLETION_EXCLUDED`）——
它们都是「事后登记」性质的记录项，缺了不影响检测结论：

| 字段 | 不参与的理由 |
|---|---|
| 报告编号 | 报告可能滞后出具，不应阻塞检测结论 |
| 照片证据 | 附件补充性质 |
| ERP处理 | 处理动作在系统外完成，登记时间不确定 |

- 规则在 `config.COMPLETION_FIELDS`，写完检测字段后由
  `repo_inspect.upsert()` 自动重算（先与库中现有值合并再判定，
  因此「只提交部分字段」的调用也能得到正确结论）
- 未完结存**空值**而非「未完结」—— 跨库判定统一用
  `completion NOT LIKE '%完结%'`，让「没检测过」与「检测了没填完」在 SQL 里一致
- 外部传入 `completion` 会被忽略（派生字段不可手工写）
- 历史数据可用 `python tools\recalc_completion.py` 重算，会列出
  **缺口分布**（缺哪个字段的记录最多），便于优先补录

### 处理登记（检测之后的跟进）

2026-09-20 从检测登记拆出 —— ERP 处理属于「检测完了之后」的环节，
与检测结论无关（也**不参与完结状况判定**，见 `config.COMPLETION_EXCLUDED`）。

| | 检测登记 | 处理登记 |
|---|---|---|
| **字段** | 检测时间 · 检测结果 · 故障原因 · 改善措施 · 处理方案 · 问题分类 · 责任归属 · 完结状况 · 报告编号 · 照片证据 | **ERP 处理** · **后续处理方案** |
| **行级口径** | 未录检测时间或未完结 | 已检测、且 ERP 处理不是「已处理」 |
| **整单清单** | 还有明细未检测或未完结 | **还有明细的 ERP 处理不是「已处理」** |
| **左侧清单** | 「待检清单」 | 「待处理清单」 |
| **数据落库** | `inspect_db` | `handle_db`（独立 schema） |

**ERP 处理是两值锁定项**（不给自由输入，也不给「请选择」空选项）：

```
已处理 / 待处理        ← 没有第三种状态，也没有"空"
```

空值在**读取时统一归一为「待处理」**（`config.HANDLE_DEFAULT_VALUES`），
历史数据已由 `tools\backfill_handle_pending.py` 一次性回填成两值。
归一与回填两件事都要有：回填让库里只剩两态，归一兜住将来导入或手工改库
产生的空值 —— 缺任一个都会出现「列表显示待处理、筛选却查不到」这类不一致。

> **待处理判定用反选**（`erp_handled <> '已处理'`）而不是正选（`= '待处理'`）：
> 处理库是稀疏存储，未处理的明细可能整行都不存在，用正选会把它们全漏掉，
> 而且不报错。

#### 左侧那个「仅看未处理」的门槛（2026-09-22 修）

处理页左侧清单按**售后单**聚合，勾上「仅看未处理」后，一单只要**任意一行**的
ERP 处理不是「已处理」，它就留下。另有一道门槛：**整单至少有一行检测过** ——
纯未送检的退回单此刻还在检测页的待检清单里，不该混进处理待办。

**「没检测」不算「未处理」。** 未检测是**检测模块的待办**，不是处理模块的。
原先整单判定写成「未检测 **或** 未处理」，于是「每行都已处理、只是个别行没录
检测时间」的单会挂在未处理清单里 —— 而界面上它的状态标签是绿色「已处理」、
未处理数 0，看着自相矛盾（实测 5 单：`20263017` / `20262921` / `20262688` /
`20262679` / `20262617`）。

> ⚠️ 别把表里那条**行级**口径（「已检测、且未处理」）抄到整单判定上：
> 两者方向相反是**刻意的**。行级问「这行检测完了吗、处理了吗」，
> 整单问「这单还有没有事没办完」。检测页的待检清单是同一个形状、相反的结论
> （那里未检测**必须**算待检，它的职责就是「把没检测的检掉」）——
> 口径取决于**模块职责**，不是能通用的规则。

> 前端那行进度文案也有个配套改动：原来拿**未检测数**当条件、却显示**未处理数**，
> 「全已处理但有行没检测」的单会显示「· 0 未处理」。现在两个数各判各的字段、
> 分开显示（「· N 未处理」「· N 未检测」）。

**后续处理方案**（`handle_solution`）是可搜索下拉：输入片段即模糊过滤历史值，
库内没有的词直接录入即自动新增为候选。它与检测登记里那个**锁定的**「处理方案」
（`solution`）是两个字段：

| | 检测登记的 `solution` | 处理登记的 `handle_solution` |
|---|---|---|
| 回答 | 这台设备怎么处置 | 这单后续怎么跟 |
| 形态 | 锁定 7 项，不接受新值 | 可搜索、可新增 |
| 影响 | **参与「完结状况」判定** | 不参与判定 |

> 候选是**重建式**的：某个值不再被任何明细引用时会从候选里回收
> （避免下拉框里堆一堆只在历史版本用过的幽灵值）。

处理页右侧会**只读展示当前行的检测结论**（故障原因 / 责任归属 / 完结状况）——
处理时要看到「这一行为什么坏、归谁」，否则只能盲填。

> **迁移**：历史数据用 `python tools\migrate_erp_to_handle.py` 搬运（带 `--dry-run`），
> 搬完会从 `inspect_records` **删掉 `erp_handled` 列** —— 两处都能存必然出现
> 「改了这处、那处还是旧值」的脏数据。命令同时重建处理库的字典候选。

### 照片证据（图片上传）

「照片证据」是图片上传控件，检测登记页与明细查询页的编辑弹窗都能传/删：

```
照片证据
┌────┐┌────┐┌────┐  ＋ 上传照片     最多 20 张，单张不超过 10 MB
│缩略││缩略││缩略│  （可多选 / 可拖拽）
└─×──┘└────┘└────┘
 点击看原图 · 每张右上角 × 删除
```

- **上传即落库**，不需要再点保存 —— 传完缩略图立刻出现，刷新页面也在
- 支持 **多选** 与 **拖拽**；点缩略图看原图（灯箱），可另存原图
- 每张会生成 `长边 320px` 的缩略图供列表快速加载，**原图完整保留**；
  生成缩略图时按 EXIF 方向自动转正（手机拍的照片常带旋转标记）
- 校验：格式白名单、单张 ≤ 10 MB、每条 ≤ 20 张；**先整批校验再落盘**，
  任一张不合格整批拒绝，不会出现「传了一半」
- 伪装成图片的文件会被 Pillow 实际解码拦下（改扩展名不管用）
- 删除记录（含批量删除）时**照片文件一并清理**，不留永远访问不到的死图

**关于金山的历史值**：金山表格该列存的是内嵌图片公式（`=DISPIMG("ID_…")`），
图片本体不在导出文件里，在新系统里解析不出图片。这类值已由
`tools\strip_photo_legacy.py` 一次性清理（5 条），导入脚本也不再写入
（`clean_photo()` 把公式视为无内容）——原始 ID 仍保留在
`data/_kdocs_returns_raw.json` 可回溯。

> 代码里保留了「无法解析的值按原文展示」的兜底：只是为了**万一有异常值落库时
> 不静默丢数据**，正常数据下不会触发。

### 两级结构的由来

退回登记是「一个快递单 → 多只产品」，所以一个售后单下可能有多条明细。
检测登记因此分两级：**左侧看「哪一单还有活」，右侧做「这一单里逐只产品录检测」**。

- 左侧清单列：售后单号 · 退回单号 · 厂家/风场 · 明细进度（`3 行 · 2 待检`）· 状态 · 登记时间
- 右侧上方是整单信息（只读），中间是该单的明细行列表（点选切换录入目标，
  已完结的行带绿色标签），下方是当前选中行的录入表单
- 保存按钮旁有「下一行 →」便于逐只产品连续录入

**整单状态取「最落后的那一行」**：

| 状态 | 判定 |
|---|---|
| 未检测 | 全单既没录过检测时间、也没有行标记完结 |
| 检测中 | 有行动过，但尚未全部完结（含录了一半的） |
| 已完结 | 全部明细都已完结 → 移出待检清单 |

> 「已检测」的口径是**有无检测时间**，与明细级过滤参数 `untested_only` 一致。

| 分区 | 字段 |
|---|---|
| **检测信息** | 检测时间（锁定）、检测结果、故障原因、改善措施、处理方案 |
| **归因与结论** | 问题分类、责任归属、完结状况、报告编号、ERP处理、照片证据 |

- **检测时间锁定为当天**：检测时间只是登记痕迹，不需要人工选择，因此与退回登记的
  「退回时间」采用同一套处理（`readonly` + `default: today`）。已有检测时间的记录
  （如历史导入数据）打开时**显示原值、不覆盖**。锁定只在检测登记页生效 ——
  要修正检测日期，到「明细查询」页编辑（该页不识别 `readonly` 标记）。
- **检测结果 / 故障原因 / 改善措施为可搜索下拉**：输入关键字即实时筛出历史候选
  （如输入「正常」筛出「加热正常，信号正常，启动正常」等），也可直接录入新值 ——
  新值提交后自动汇入候选。候选来自检测登记库的累积（当前 16 / 12 / 4 个）。
- **处理方案 / 问题分类 / 责任归属为纯下拉锁定项**（选项在 `config.FIXED_OPTIONS`
  集中维护，不接受自由输入）：

  | 字段 | 选项 |
  |---|---|
  | 处理方案 | 维修入库 · 检测入库 · 拆解报废 · 供方分析 · 维修返回 · 原件返回 · 拆解入库 |
  | 问题分类 | NTF · 客户应用 · 制程问题 · 来料问题 · 设计选型 · 产品设计 · 无法判断 |
  | 责任归属 | 贝良端 · 客户端 · 供应商端 · 其他端 |

  锁定是为了**保证统计口径统一** —— 可搜索下拉虽灵活，但同一含义容易出现多种
  写法（历史上「无法判定」与「无法判断」就并存过）。明细查询页的筛选面板会自动
  使用同一份清单，不需要单独维护。
- **扫码定位**：扫产品编号 / 料号 / 退回单号 / 售后单号 → 定位到它**所属的售后单**，
  并自动选中对应明细行；该单不在当前清单（比如已全部完结）时会明确提示。
- **只写检测字段**：产品信息与整单信息在面板中只读展示，避免检测岗误改登记内容。
- 「仅看待检」开关可切换到全部单据；清单支持关键词检索与分页（每页 50 单）。
- 保存走 `PUT /api/returns/{detail_key}`（**按明细行**保存）。
- 清单接口 `GET /api/inspect/orders?pending=1` 返回按售后单聚合的结果；
  取某单下的明细用 `GET /api/returns?order_no=…&sort_by=line_no`。
- 明细级的 `inspect_pending` / `untested_only` 过滤参数保留，
  仍可用于「按明细筛选」（如导出、明细查询）。

### 扫码登记的三种输入方式

1. **扫码枪**：USB-HID 键盘模拟型扫码枪，无需驱动。页面全局监听键盘输入，
   连续快速输入 + 回车即判定为扫码，**不需要先点击输入框**。
2. **手动输入**：在顶部大输入框键入条码，输入停顿约 240ms 后自动匹配；
   支持只输入条码后几位（模糊后缀匹配）。
3. **摄像头**：点击「摄像头扫码」调用本机摄像头，用 ZXing 解码条码/二维码。

> 摄像头受浏览器安全策略限制，需通过 `http://127.0.0.1:8000`（本机）或 HTTPS 访问。
> 若同事通过局域网 IP 访问且浏览器未放行摄像头，请改用扫码枪或手动输入。

### 下拉框的两种形态

| 形态 | 适用字段 | 行为 |
|---|---|---|
| **可搜索下拉** | 风机厂家、项目风场、产品型号、产品类别、品名、规格、反馈现象、问题分类、责任归属等 | 输入关键字实时过滤库内已有值，右侧显示使用次数；**库内没有时显示「＋ 使用新值」**，选中即录入，提交后自动汇入候选 |
| **纯下拉** | 快递归属、分析报告、快递公司 | 快递归属锁定 `销售端` / `售后端`；分析报告锁定 `是` / `否`；快递公司锁定 `config.CARRIER_OPTIONS` 中的 10 家。均不接受自由输入，选项在 `config.FIXED_OPTIONS` 中集中维护 |

### 快递公司自动识别

录入退回单号时按前缀实时识别快递公司，规则表在 `config.CARRIER_PREFIX_RULES`：

| 单号前缀 | 识别结果 |
|---|---|
| `SF` | 顺丰速运 |
| `JD` | 京东物流 |
| `YT` | 圆通速递 |
| 纯数字 | 无法识别 → 手工选择 |

- **只在快递公司为空、或当前值是系统上次自动填入时才改写**；人工选择过则保留人工值。
- 单号前缀变化时（如先输 `SF…` 后改为纯数字）会清掉自动填入的值，回到待选状态。
- 字段下方实时提示：`✓ 已按单号前缀识别为顺丰速运` / `单号为纯数字，无法自动识别，请手工选择`。
- 后端 `create_returns_batch` 与 `create_return` 同样做识别兜底，导入脚本等非页面调用方结果一致。

### 产品信息的候选与自动回填（2026-09-22）

明细行（登记页 / 扫码页 / **明细查询的二级弹窗**）里，产品信息这一组**全部从匹配数据库取候选**：

| 字段 | 候选来自匹配库的哪一列 |
|---|---|
| 料号 `material_no` | `material_no`，且**任意列搜索**（也支持按品名 / 型号找料号）|
| 产品型号 `product_model` | **`spec`**（本系统「产品型号」= 规格）|
| 产品类别 `product_category` | **`production_stat`**（名为 `category` 的那列是空的）|
| 品名 / 规格 / 生产统计 | 同名列 |

**选中料号 / 产品型号 / 规格**后会自动回填同组的其它字段（数据来自 `/api/items/fill`）。
「产品类别」**不作为回填入口** —— 一类多料，拿类别查不到唯一物料，它只填自己。

回填遵守**人工优先**：只填空格，或覆盖「上一次由系统自动填入」的值；已被人工改过的格子永不改写。

> 两个接口的分工别混：`/api/items/search` 是「任意列匹配、返回整条物料」（找料号用），
> `/api/items/options?field=X` 是「**按 X 对应的列**匹配、返回该列的去重值」——
> 在「产品型号」格里搜 51177，候选必须是型号值本身，用错接口会填出一堆料号。
> 字段→列的映射在 `core/repository.py` 的 `ITEM_FIELD_COL`。
>
> 另外：二级弹窗的字段控件必须**同时**覆盖 `search-item` 与 `search-dict`。
> 只判前者的话，`search-dict` 那串字段（产品型号 / 类别 / 反馈现象 / 检测结果…）
> 会落到 `else` 分支变成**普通输入框**，没有任何候选 —— 而语法检查与"控件存在"类断言
> 都发现不了（`check_frontend.js` 现在钉住了这个分支条件）。

### 实时匹配规则

输入任意条码后，系统按顺序精确匹配以下字段：

`退回单号 → 产品编号 → 料号 → 售后单号 → 产品型号`

精确未命中时，自动降级为后缀匹配、再降级为包含匹配。命中后：

- 扫到**快递单号**：回填整单信息（退回单号、厂家、风场、快递归属等）；
- 扫到**产品码**：自动新增一行，回填产品信息与型号字典匹配结果；
- 点「查看历史」可浏览同条码的全部历史记录，一键套用为新行；
- 历史库与型号字典均无记录时，新增空白行等待手工补全，不阻断流程。

### 导入方式

**页面导入（推荐）**：进入「匹配数据库」→ 导入 Excel → 选模式 → 上传。

| 模式 | 行为 | 适用 |
|---|---|---|
| 按料号覆盖更新 | 只影响文件里出现的料号，其他记录保留 | 增量补录，日常首选 |
| 先清空整表再导入 | 整表刷新 | 拿到新版 Item Master 时 |
| 只补空字段（`--fill`） | 本地已有值一律不动，导入值为空的也不写入 | 从 ERP 快照回填老数据 |

**命令行导入**：

```bat
.venv\Scripts\python.exe tools\import_item_master.py "路径\ItemMaster20260905.xlsx"
.venv\Scripts\python.exe tools\import_item_master.py "路径\ItemMaster.xlsx" --replace
.venv\Scripts\python.exe tools\import_item_master.py "data\exports\物料主档_ERP.xlsx" --fill --pad-old-no --dry-run
```

最后一行是**回填老数据**的配方：`--fill` 只补空；`--pad-old-no` 给旧料号补前导 0
（ERP 的 Seg5 是数值字段，`012100100` 读出来是 `12100100`，而本地 1429 条已有值里
1428 条正好等于「0 + ERP 值」→ 照本地风格补，库里就不会两种写法并存）；
`--dry-run` 先空转说明会改哪些字段、多少行，确认后再去掉它真跑。
2026-09-22 用它补了 11445 行：品名 11444 · 旧料号 8905 · 描述 4733 · 客户 716 ·
量程/输出/防护 279。

> 生产统计列本地存的是**中文类别名**（如 `风速【低温】`），而 ERP 快照里那列是**内码**
> （如 `2338`）。导入脚本遇到纯数字的内码会跳过并报数 —— 往名字列写编号等于灌脏数据；
> 内码翻译是 `core/erp_sync.py` 的活（查 `Base_DefineValue`，权限不够时宁可留空）。
>
> 为什么必须有 `--fill`：`upsert` 会把文件里的值覆盖到本地（含空值），
> ERP 账号只给三列时跑一次就把人工整理的品名清成空（2026-09-22 实测）。

表头需含「料号」列，可识别的列为：旧料号、料号、品名、型号、规格、描述、客户、
生产统计、产品量程、信号输出、防护等级、产品类别。料号为空的行会被跳过，其余列忽略。

> `产品量程 / 信号输出 / 防护等级` 三列同时兼容旧表头名 `标参1 / 标参2 / 标参3`，
> 源文件表头改不改都能正常导入。

### 与 ERP 自动同步（2026-09-21 新增）

匹配库直接连 ERP 定时刷新，不必再人工拖 Excel 进来。
界面在「匹配数据库」页顶部的**「ERP 物料主档同步」卡片**：状态、最近同步时间、
写入范围（**整表覆盖后哪些列会变空**）、手动「立即同步」、自动同步开关、连接配置。
⚠️ 同步是**整表全量覆盖**（2026-09-22 用户确认），是个破坏性动作 ——
所以「立即同步 / 自动同步开关 / 修改连接配置」这三个写操作只有拿到
`act.items_sync`（默认只给管理员）才渲染；没有权限的人照样看得到状态卡，
只是不给按钮（点了必然 403，看起来像坏了）。

| 接口 | 用途 | 权限 |
|---|---|---|
| `GET /api/items/sync/status` | 状态（**永不回读密码**，只给 `password_set`）| 登录即可 |
| `POST /api/items/sync/run` | 手动触发（后台跑，立即返回；前端轮询状态）| `act.items_sync` |
| `PUT /api/items/sync/config` | 改配置（密码只写不读：留空＝不改，传 null＝清除）| `act.items_sync` |

**凭据**：环境变量优先，其次是页面填写（存 `auth_db.setting`）。
代码里**没有默认密码** —— 缺了会明确报错，而不是拿一个写死的弱口令去连生产库。

ARS_ERP_USER=sh_report_user
ARS_ERP_PASSWORD=******        # 必填，代码里没有默认值

#### 读取范围：11 列，**全部实时**（2026-09-22 改版）

**一条 SQL 取全**（主表 LEFT JOIN 多语言表），不再依赖任何离线快照、
也不再有「ID → 料号」的桥：

| ERP 列 | 本地字段 |
|---|---|
| `A.Code` | `material_no` 料号 |
| `A.Code1` | `model_no` 型号 |
| `A.SPECS` | `spec` 规格 |
| `A.Name`（**主表**） | `product_name` 品名 |
| `B.Description`（多语言表） | `description` 描述 |
| `A.DescFlexField_PrivateDescSeg5` | `old_material_no` 旧料号 |
| `A.DescFlexField_PrivateDescSeg4` | `customer` 客户 |
| `A.DescFlexField_PrivateDescSeg3` | `production_stat` 产品类别（内码 → 分类表翻译） |
| `A.DescFlexField_PrivateDescSeg8/9/10` | `param1/2/3` 标参1-3 |

**权限已于 2026-09-22 全部放开**（7 列 `ID` + 6 个 `DescFlexField_*`，
另加 `Name`），同步实测跑通：`ok=true · missing_cols=空 · 8.87 秒 · 13195 行`。
品名从 13178 → **13195（0 空）**，那 17 个快照时代漏掉的料号一次补齐。

> **缺权限时的行为**（留着备查）：同步会失败并在状态里写明「读不到哪一列」
> （`missing_cols`，界面直接显示红字），**匹配库保持原样不动** ——
> 宁可停在旧数据，也不让半份数据覆盖进去。这一点有实测记录：
> 无权限时同步前后都是「13195 行 / 品名 13178」，一个字节没动。

**两个刻意的取舍**（2026-09-22 权限重配后定，都写在 `ITEMS_SQL` 下的注释里）：
1. **品名取主表 `A.Name`**，不取 Trl 的 `NameCombineName` —— 后者被权限收窄掉了。
   实测 `A.Name` 与库里原有 13178 个品名**完全一致**（规格列做对照：13195/13195 全等），
   余下 17 个是「本地空、ERP 有值」，正好补上。
2. **JOIN 不带 `B.SysMLFlag = 'zh-CN'`** —— `CBO_ItemMaster_Trl` 的 ID 实测**全局唯一**
   （13195 行 / 13195 个 ID），是单语言表，多语言过滤没有意义；该列同样被收窄不可读。

授权语句（发给 ERP 管理员即可，多给了 `Name` 一列留着将来用）：

```sql
GRANT SELECT ON dbo.CBO_ItemMaster(
    ID, Name,
    DescFlexField_PrivateDescSeg3, DescFlexField_PrivateDescSeg4,
    DescFlexField_PrivateDescSeg5, DescFlexField_PrivateDescSeg8,
    DescFlexField_PrivateDescSeg9, DescFlexField_PrivateDescSeg10)

```

> 于是那段时间是「实时 3 列 + 离线快照补 6 列 + ID→料号 桥」，快照冻结在 09-21，
> 之后新建的料号拿不到补充列（实测 17 个）。**2026-09-22 用户决定去掉快照、

每次先 `DELETE FROM items_db.item_master` 再插入这次从 ERP 取回的行；
ERP 已删除的料号本地也跟着消失。整表覆盖**不再等于清空字段** ——

#### 老数据的品名/旧料号/描述是空的：用快照回填

> ## ⛔ 2026-09-22 起本节做法**已作废** —— 仅作历史留存
>

#### 调度（2026-09-22 改成墙上时钟）

后台节拍器（`core/sched.py` 的 `Ticker`）**每分钟醒一次**，比较「上次同步时间 +
间隔」与当前时间，到点才真正开跑。不用「睡够整个间隔再醒」是因为后者有三个坑：
配置改完（启用/关闭/改间隔/补密码）要等整整一轮才生效；停机期间错过的到点
永远补不回来；睡的是**时长**而不是**到点时刻**，休眠或时钟跳变会整段跳过。

- 匹配数据库默认 12 小时，走**整表覆盖**（`mode="replace"`）：ERP 账号读不到
  `ModifiedOn`，没有增量依据；发货明细默认 8 小时且走**常规同步（增量）**。
- 发货明细的自动同步**只刷两类单**（2026-09-22 定）：①当天与前一天的
  `BusinessDate`；②本地还没核准（草稿 / 开立 / 核准中）的单据 —— 只有这两类
  才是 ERP 侧还会变的。未核准的单**在 ERP 被删掉后，本地也跟着删**。
  要整表重拉用页面上管理员专属的「**全量同步**」（`POST /api/delivery/details/sync/full`，
  先清空整张 `ship_detail` 再全量写回）；「立即同步」只走常规增量。
  **日期区间入口已彻底去掉** —— 两条路都不需要用户填日期，留着等于给
  「点一次就把 8.9 万行换成一段区间」留后门（`POST /sync` 现在**忽略**请求体里
  的 `date_from`/`date_to`，[29] 守着这条）。
  - 取数只发**一条 SQL**（`(日期窗口) OR a.DocNo IN (…)`）。拆成两次查询，
    「既在窗口里、又未核准」的单会被取回两次，而这张表没有天然唯一键、
    落库又是先删后插 —— 行数会直接翻倍。
  - 单号清单上限 800（`PENDING_DOC_LIMIT`），给 MSSQL 单语句 2100 个
    参数上限留余量；**删除与写回用的是同一个谓词**，两处不一致就会留下
    永不更新的旧行，或者删掉没重新取到的行。
  - 「取回 0 行就中止替换」这条保命守卫只在**增量**路上放宽：先用
    `SELECT TOP 1 a.DocNo FROM dbo.SM_Ship` 探活（**不能**用 `COUNT(*)` ——
    这个账号是列级授权，`COUNT` 必报错 230），确认账号看得见数据，才按
    「这些未核准单已在 ERP 删除」执行删除。
- 手动「立即同步」与定时触发**共用一把锁**，不会并发写库。
- 页面上直接给出**下次自动同步的时间**（状态接口的 `next_at`）—— 不必再猜
  「它到底排上了没有」。
- 这一段是应用内的定时，不需要 cron / systemd timer。
- ⚠️ 「启用自动同步」开关读的是 `enabled`（**有没有启用**），不是 `running`
  （**此刻有没有同步在跑**）。早先绑错了字段：`running` 绝大多数时候是 false，
  开关就永远显示「关」，用户点一下、下次渲染又变回「关」，于是断定
  「自动同步不生效、只能手动点」—— 而后端其实一直在按时跑。
  守卫在 `tests/check_frontend.js` 的 `[13]`，后端侧的证据在
  `tests/smoke_test.py` 的 `[31]`。

> **每个任务有自己的 ERP 连接**（2026-09-22 起）：匹配数据库读 `auth_db.setting` 的
> `erp_*`（环境变量 `ARS_ERP_*`），发货明细读 `ship_erp_*`（`ARS_SHIP_ERP_*`）。
> 在「自动同步任务」页点哪张卡的「连接配置」，改的就是那一份，**不动另一个**。
> 拆开之前是共用一份 —— 那种模式下「改一处忘另一处」在界面上完全看不出来
> （两张卡都显示正常，只有一个在后台连不上），这正是拆开它的理由。
> 升级时的搬运只做一次：`core/erp_ship.ensure_conn_seeded()`（看 `ship_erp_seeded` 标记）。
>
> **开关与间隔也是各存各的**：发货明细用 `ship_detail_auto_enabled` /
> `ship_detail_auto_interval_hours`，匹配数据库用 `erp_enabled` /
> `erp_interval_hours`。**空值一律删键、回落默认值**，表里不留「显式空值」——
> 那种值看着像没配、实际在生效，直接看库的人必然读错（`core/erp_conn.py`）。

```bat
python tools\pull_erp_itemmaster.py            :: 覆盖式刷新
python tools\pull_erp_itemmaster.py --stamp    :: 文件名带时间戳，保留历史快照
```

> 这套表是**用友 U9** 的基础档案 —— 不是 SAP B1，也不是金蝶。判据：`ItemSource`
> 列全表为 `U9`，同实例存在 `U9toQC` 库，表结构是 U9 特有的 `CBO_` +
> `Segment1..30` / `NameSegment1..30` + `DescFlexField_*` 特征字段体系。

**两个必须知道的坑**（脚本里已绕开，改脚本时不要踩回去）：

1. **字符集**：pymssql 默认 `charset=UTF-8` 时，FreeTDS 在本机 build 里装配
   `utf-8 ↔ UCS-2LE` 转换失败，登录包直接被服务端拒回
   （`Error converting characters into server's character set`）。实测可用值只有 `cp936`。
2. **但 cp936 不能用来读文本列**：FreeTDS 把 nvarchar 转 GBK 时按**字符数**而非
   字节数分配缓冲，中文字符被截在半个上，客户端解 GBK 直接抛
   `'gbk' codec can't decode byte 0xb0`。实测必挂 10 列 —— `Name`、`SPECS`、
   `Code1`、`NameSegment1`、`DescFlexField_PrivateDescSeg8/9/17`，以及 Trl 的
   `Description`、`NameCombineName`、`DescFlexField_CombineName`。
   **这不是「少数列偶发」**：某列当前没中文就不报错，等录进中文才炸。
   所以**所有文本列一律 `CAST(col AS VARBINARY(MAX))` 取原始字节、本地按
   `utf-16-le` 解码**，非文本列原样取。
   脚本为此带了**长度交叉校验**（远端 `MAX(LEN())` vs 本地实际最长值）——
   这个坑若被改回直读，症状会从「报错」退化成「静默少字」，只有长度比对抓得住；
   校验不过直接 `exit 2`，不产出可疑文件。

`Picture`（varbinary）**不进 CSV**：单字段可达 691 KB，撞穿 `csv` 模块默认的
`field_size_limit=131072`，Excel 与 pandas 会一并打不开。改为落到 `data/erp/blob/`，
CSV 里只留相对路径；覆盖刷新时按列名前缀清理上一轮残留文件。

`pymssql` **刻意不写进 `requirements.txt`** —— 这是离线取数工具，不属于系统运行时
依赖，写进去只会让部署多一个必然失败的坑。

拉完实测的字段落点，供后续把 ERP 对齐进匹配数据库时参考：

| **型号** | **`Code1`** | 如 `BLF1-S` / `BLF1-SIII`，8055 种去重值 |
| ？ | `Code2` | 图号 / 物料组编号，如 `012203300` |

## 数据模型

采用**一个模块一个库**：六个独立的 MySQL **schema**，用同一个连接（连接时把六个
schema 都挂上），跨库 JOIN 的写法和单库完全一致。退回 / 检测 / 处理三库用 `detail_key`
（明细唯一键）互相关联；**发货申请库自成一套**（主表 + 明细子表，关联键是 `request_no`），
不挂在 `detail_key` 上 —— 它不参与明细查询、关键词检索与完结判定。

> 2026-09-22 之前是六个 SQLite `.db` 文件（`ATTACH` 到同一连接），为了并发写与
> 集中备份改成了 MySQL 8。**换的是引擎，不是模型**：schema 名与原文件名一一对应
> （`returns.db` → `returns_db`），表结构、跨库 JOIN、key 关联全部照旧。

```
MySQL 8（六个 schema，一个连接）
├── returns_db   退回登记库  ─── returns        30 列（整单 + 产品明细 + 登记信息）
│                               ├─ model_dict    型号字典（登记时自动积累）
│                               ├─ dict_option   本节字段的下拉候选
│                               ├─ op_log        操作日志
├── inspect_db   检测登记库  ─── inspect_records  13 列（检测 + 归因结论）
├── handle_db    处理登记库  ─── handle_records    1 列（ERP 处理）
│                               ├─ dict_option   本节字段的下拉候选
│                               └─ op_log        操作日志
├── delivery_db  发货申请库  ─── delivery_request       14 列（整单信息 + 系统字段）
│                               ├─ delivery_request_item  发货明细（一行一种产品，
│                               │                         UNIQUE(request_no, line_no)）
│                               ├─ delivery_shipment     发货记录（型号级；出队落点，
│                               │                         也是 ERP 发货清单的落地表）
│                               ├─ ledger_clear          核销记录（15 列；kind='link'
│                               │                         手动核销关联 / 'clear' 手工清账，
│                               │                         均绑退回单号与返件 id，原因必填）
│                               ├─ ship_detail           ERP（U9）出货明细镜像（16 列；
│                               │                         整表替换式同步，本地只读，
│                               │                         不参与台账核销）
│                               └─ op_log               操作日志
├── items_db     匹配数据库  ─── item_master    16 列（物料主档，随 ERP 同步增删）
└── auth_db      接入库      ─── users / permission_group / session / setting /
                                op_log / open_api_log（**唯一不可再生**）

data/photos/     照片证据  ─── <售后单号>/<明细键>-NN.<ext>  原图
                              └ <明细键>-NN.thumb.jpg      缩略图（长边 320px）
```

### 数据看板：返件汇总 / 检测汇总

看板分两个页签，按**模块职责**切分 —— 与登记模块的划分一致：

| | 返件汇总 | 检测汇总 |
|---|---|---|
| **回答什么** | 收了多少 · 从哪来 · 集中在哪 | 检了多少 · 多快 · 问题出在哪 |
| **KPI** | 返件记录 · 退回数量 · 售后单数 · 涉及型号 · 涉及厂家 · 本月新增 | 已检测 · 待检测 · 检测覆盖率 · 平均检测时长 · 7 天内检测率 · 已检测未完结 |
| **趋势** | 按**退回时间** | 按**检测时间**，另加「返件 ↔ 检测 对比」看同期积压 |
| **图表** | **产品类别 TOP** · 风机厂家 TOP · 生产年份分布 · 快递归属 · 厂家×类别交叉 | 检测趋势 · **TOP 厂家** · **厂家→主要产品类别** · **产品类别×故障原因** · 故障原因 · 问题分类 · **责任归属统计** |
| **筛选条** | 返件侧 7 项 + 退回时间区间 | 检测侧 6 项 + 检测时间区间 |

两个页签的筛选条件**各自独立**：切页签时整条筛选条重建、日期口径跟着换
（退回时间 ↔ 检测时间），互不串味。

**口径差异是有意为之**：检测数据稀疏存储（未检测的明细在检测库没有行），
所以检测汇总只统计**已检测**明细（`repository._TESTED_SQL`）。若按全部返件统计，
故障原因这类归因图会混入一大块空值，「检测量」也就不再是检测量。

**检测汇总也做了一轮精简**（现 7 张）：检测趋势 · TOP 厂家 ·
厂家→主要产品类别 · 产品类别×故障原因 · 故障原因 TOP · 问题分类 · 责任归属统计。
已移除：产品型号 TOP、返件↔检测对比、检测结果构成、处理方案、改善措施 TOP、
故障原因×责任归属 —— 同样，这些字段仍在表格、编辑弹窗与筛选条里可用。

**返件汇总只留「能直接指导行动」的维度**：趋势 · 产品类别 · 风机厂家 ·
生产年份 · 快递归属 · 厂家×类别交叉。已按需求陆续移除：产品型号 TOP（粒度太细）、
反馈现象 TOP、项目风场 TOP、快递公司、登记人分布 —— 这些字段本身仍在表格、
编辑弹窗与筛选条里可见可用，只是不做成图表。

**产品类别只留一张图**：返件汇总里的「产品类别 TOP」是横条图（有数量轴、
能读出具体条数），原先那张同数据的「产品类别分布」饼图已去掉 ——
两张图讲同一件事只会占地方。同理，返件汇总也不再按「产品型号」分组：
型号粒度太细、与厂家/类别的高频信息重叠（检测侧另有「厂家 → 主要产品」下钻）。

**刻意不做「快递公司」「登记人」**：图与筛选都不放 —— 快递公司 10 个候选逐个看
价值低（退回单号本身就能定位物流），登记人当前基本只有一人登记（饼图恒为单色、
下拉也只有单值，选了等于没筛）。这两个字段本身照旧在表格与编辑弹窗里可见可改，
需要时在 `dashboard.html` 的 `charts` / `filters` 里各加回一行即可
（图表需同步在 `stats_dashboard` 加回分组查询）。

**检测汇总的三块专项统计**：

| 想回答 | 怎么做 |
|---|---|
| **哪些厂家在返检 · 主要坏在哪类产品** | `TOP 厂家`（横条图，按检测条数）+ `厂家 → 主要产品类别`（**条形组**：每厂家一组，组内是各类别的占比条） |
| **各类产品都在坏什么** | `产品类别 × 故障原因`（堆叠柱状图，左轴类别 TOP 8；**原因轴不截断**，用卡片右上角「筛选」控制显示项） |
| **责任归谁** | `责任归属统计`（横条图，条数）+ `故障原因 × 责任归属`（交叉） |

> **「厂家 → 主要产品类别」为什么不用画布**：每个厂家的构成要独立成组，
> 堆进同一张堆叠图里颜色会打结；用 HTML 条形组（`type: 'bars'`）
> 让每个厂家各自一行，标签也能完整显示。
>
> **下钻维度用「类别」而非「型号」**：类别粒度跨厂家可比，能回答
> 「这家返检集中在哪类产品」；型号是厂家专属的（金风 `BLJJ` / 明阳 `BLJT`），
> 互相不通，只适合精确到料号的场景。`stats_vendor_products(item_field=…)`
> 两个维度都支持，改参数即可切换。

> **故障原因轴不截断**：早期版本会收口到 TOP 6、其余并入「其他」——
> 但那会把你想看的项藏进聚合值里。现在后端返回全部原因，改由卡片内的
> **「筛选」按钮**勾选要展示哪几项（默认全选）。勾选后颜色保持不变
> —— 按原始序号取色，不会因为勾掉一项就让其余颜色整体前移。

> 「待检数」「检测覆盖率」是例外 —— 它们**必须**含未检测记录才有意义，
> 因此退回全量口径单独计算（见 `stats_inspect_overview`，不走 scope 收窄）。
> 已检 / 待检用两个互补条件，同一批记录不会两边都算。

**检测时效口径**：退回后 **7 天**内完成检测算「及时」，阈值即
`repository.FAST_TEST_DAYS`。当前平均检测时长约 34 天，这一项因此只有个位数
百分比 —— 阈值调宽后数字会更贴合实际节奏。

接口：`GET /api/stats?scope=return|inspect&granularity=month|week|day&<筛选>`

> **踩过的坑 —— 新增筛选项要改三处**：`app.list_returns` 与 `app.export` 的
> 参数签名、`repository._build_where` 的精确匹配清单。FastAPI 只认签名里声明过
> 的查询参数，漏了**不报错**，条件被静默丢弃 —— 界面上选了筛选却返回全量，
> 比报错难发现得多。自检里有一条 AST 校验守着这三处一致（详见「自检」章节）。

### 批量删除（接口保留，界面入口已下线）

明细查询页**不再提供勾选删除的界面入口**（方案 B），接口仍然可用：

- `POST /api/returns/batch-delete`，body `{detail_keys: [...]}`，单次上限 2000 条
- 删除会**同时清理关联的检测记录**，并回收字典候选与型号字典
- 删除前会先落**回收站**（整行快照，保留 7 天，可还原）

> 之所以不逐条调用 `DELETE /api/returns/{key}`：后者每删一条都会触发一次
> **全量字典重建**（对每个字典字段做 GROUP BY 全表扫描），删 100 条就是 100 次重建。
> 批量接口在同一次事务内删完，字典只在最后重建一次。

**明细查询 = 两个业务库拼接**：

```sql
SELECT r.*, i.test_date, i.test_result, ..., h.erp_handled
FROM returns r
LEFT JOIN inspect_db.inspect_records i ON i.detail_key = r.detail_key
LEFT JOIN handle_db.handle_records  h ON h.detail_key = r.detail_key
```

> **必须用 LEFT JOIN。** 检测记录是**稀疏存储**的 —— 没检测过的明细在检测库里
> 根本没有行。用 INNER JOIN 会让所有未检测记录从查询、看板、导出里整体消失。
> 同理，对检测侧字段做条件判断时必须 `COALESCE` 兜底：
> `NULL NOT LIKE '%完结%'` 的结果是 NULL（不成立），会漏判未检测记录。

### 写入为什么不会跨库

退回登记只写 `returns_db`，检测登记只写 `inspect_db`，处理登记只写 `handle_db`。
一条写入只落一个 schema —— 跨库事务的语义与回滚限制不必再考虑，
这既是 MySQL 改造前的约束（SQLite 的 `ATTACH` 不提供跨库原子事务），
也顺手让「一次写入改一个模块」这条铁律在代码里看得见。

仅两种低频操作会触及两库：`PUT /api/returns/{key}`（按字段归属分流）
与删除记录（两库各删各的）。它们**不是原子的** —— 极端情况下可能出现
「退回侧已删、检测侧残留」。这是可接受的取舍，也已写进代码注释。

### 从旧版单库升级

旧版本把 43 个字段全塞在一张 `returns` 表里。迁移脚本会自动完成拆分：

```bat
python tools\migrate_to_multidb.py
```

- 检测字段 → `inspect_db.inspect_records`（迁移前**自动整库备份**到
  `data/backup_legacy_*/`，确认无误后可删）
- `item_master` → `items_db`
- 脚本可重复执行，已迁移的部分自动跳过

> ⚠️ `tools/migrate_to_multidb.py` 与 `tools/migrate_erp_to_handle.py` 等
> 都是 **SQLite 时代的迁移脚本**，只对 `data/*.db` 旧库有效；
> MySQL 之后不要再用它们（各脚本开头已加同样说明）。

日常启动时也会自动清理旧结构（幂等），不需要每次手动跑。

### 从金山文档导入历史数据

```bat
python tools\import_kdocs_returns.py             # 导入全部（追加）
python tools\import_kdocs_returns.py --replace   # 先清掉上批金山导入，再整表重导
python tools\import_kdocs_returns.py --limit 20  # 只导前 20 条
python tools\import_kdocs_returns.py --dry-run   # 只预览映射，不写库
python tools\import_kdocs_returns.py --no-rekey  # 保留金山原样单号（会破坏单号不变量）
```

> ⚠️ **`--replace` 会把你手工删掉的记录带回来**：它清的是 `source='kdocs'` 的全部行再重导，
> 而源表里还在的记录会重新出现。库里已经手工清理过数据、又只想补某几列时，
> 用 `tools/backfill_inspect_placeholders.py`（只 UPDATE 已有行、只补空值）而不要重导。

数据源为 `data/_kdocs_returns_raw.json`（金山表格选区读取后保存的规范化数据）。

| 金山列 | 去向 |
|---|---|
| 售后单号 · 风机厂家 · 项目风场 · 产品编号 · 产品型号 · 产品类别 · 生产年份<br>退回数量 · 退回时间 · 退回单号 · 信息来源 · 反馈现象 · 备注 | **退回登记库** |
| ERP处理 · 检测时间 · 完结状况 · 检测结果 · 故障原因 · 改善措施<br>处理方案 · 问题分类 · 责任归属 · 照片证据 · 报告编号 | **检测登记库** |
| 快递费用 · 是否待返回 · 回复进度 | **跳过**（系统已移除这三个字段） |

自动处理：

- **快递公司**按退回单号前缀识别（`SF…` → 顺丰速运）；单号不是标准前缀的
  （如有人直接把「韵达3129…」填进退回单号）会留空，需人工在明细查询页补选；
- **售后单号归一**：金山是「一行一个售后单号」，导入时按快递单合并成
  「一个快递单 ↔ 一个售后单、多产品各占一行」（本库的铁律，见数据模型章节）；
- 明细唯一键与行号自动生成（`20260001-001`）；
- **占位符分两侧两种口径**（2026-09-22 修，别混用）：
  - **退回侧**：`/`、`—`、`无` 等清洗为空（它们在这边就是"没填"）；
  - **检测侧**：`/` **保留** —— 它是金山侧人工填的「本栏不适用、已确认过」，
    而检测字段是完结状况的判定依据，清掉会把已确认的单判成未完结
    （实测曾是 3007 条 vs 166 条）。其中三列换成更准确、且在锁定清单内的词：
    **故障原因「/」→「NTF」**、**改善措施「/」→「暂无改善」**、
    **处理方案「/」→「拆解报废」**（`solution` 是固定选项字段，`/` 不在清单里）；
- **照片证据**列的内嵌图片公式（`=DISPIMG(…)`）视为无内容 —— 图片本体不在导出文件里，
  落库只是干扰；真照片由检测登记页上传；
- 日期统一为 `YYYY-MM-DD`；
- **ERP处理**列金山是自由文本（「已入返修库」「退回供应商」…），而本库该字段是
  **两值锁定**，导入时降维：凡「ERP 侧动过」的写法一律归「已处理」，空值归「待处理」
  （原始文本留在快照里可回溯）；
- 导入的记录标记 `source='kdocs'`（数据来源）—— 便于日后回溯这批历史数据。

### 关键字段规则

- **明细唯一键** = `售后单号-行号`（如 `260918001-001`）。**一个快递单下可有多个明细行，
  一行对应一只产品**，行号在所选售后单号下连续递增。

> **结构不变量：一个快递单号 ↔ 一个售后单号。**
> 同一快递单寄回多只产品时，它们**共用一个售后单**，各自占一行（行号自 1 连续递增）。
> 这条约束有三重作用：扫快递单号补登时能唯一定位到目标单；检测登记按单聚合时有确定的行集合；
> 单号与快递单可互相印证。
>
> 历史数据曾出现「同一快递单被拆成 34 个售后单」的情况（金山导入时一条明细一个单），
> 已用 `tools/merge_orders_by_return_no.py` 梳理为 100 条明细 / 34 个售后单。
> 该不变量已写进自检断言（第 [21] 节），将来若再出现分裂会立刻报警。

> **完结状况是派生字段。** 判定依据为 `config.COMPLETION_FIELDS` 中的 7 项
> 检测字段（报告编号 / 照片证据 / ERP处理 不参与）。规则调整后可用
> `python tools\recalc_completion.py` 一次性对齐历史数据。
- **售后单号自动生成规则**：`年份后两位 + 月日 + 3 位顺序号`，顺序号**按日重置**。

  | 日期 | 当天第几单 | 单号 |
  |---|---|---|
  | 2026-01-01 | 第 1 单 | `260101001` |
  | 2026-01-01 | 第 2 单 | `260101002` |
  | 2026-01-02 | 第 1 单 | `260102001` |

  登记时**留空即自动生成**；若要往已有售后单里追加明细，填入该单号即可。

### 补登与查重

**售后单号不接受手工填写**，由系统按快递单号（退回单号）自动判定归属：

| 情形 | 系统行为 |
|---|---|
| 快递单号在库中不存在 | 生成当日新单号（如 `260918001`） |
| 快递单号已登记过 | **自动补登**到该快递单所属的售后单，行号续接（如 `-004`） |

录入快递单号后，页面会实时提示本次是「新单」还是「补登至某单」，
售后单号栏同步显示该编号但不可编辑。

**重复登记会被拦截**。判定方式：同一快递单号下，某行的产品标识
（依次取 `产品编号 → 料号 → 产品型号 → 品名` 的第一个非空值）与库中已有记录相同时：

1. 录入过程中页面立即出现红色告警条，列明第几行、哪个字段、与哪条记录重复；
2. 点提交时弹出明细对照表并**阻止提交**；
3. 后端接口同时返回 `409`，即使绕过前端也无法写入重复数据。

> 若确为同型号的另一件产品，请把数量合并到已有记录，或修改产品编号以便区分。
- **行级独立**：检测信息（检测时间、反馈现象、检测结果、故障原因、改善措施、处理方案）
  与根因归类（问题分类、责任归属、完结状况、报告编号等）都挂在**行**上，
  同一快递单里的多只产品各自独立关联，互不影响。
- **整单共享**：退回单号、快递公司、退回时间、快递归属、风机厂家、项目风场、售后单号、
  备注、登记人填一次即作用于该单下全部明细行。
- **型号字典** `model_dict`：登记时自动积累「型号 → 类别/品名/规格/料号」映射，
  后续扫到产品编号即可反查回填。
- **字典选项** `dict_option`：所有可搜索下拉的候选值从现有数据自动汇总，无需手工维护；
  下拉框内录入的新值提交后会自动汇入候选，下次可直接选。
  字典采用**重建式**同步 —— 每次登记后按当前数据重新生成候选集，不在集合内的
  旧值会被自动清除。因此删除记录、改错字段后，下拉框里不会留下无效选项。
- **派生表回收**：`dict_option` 与 `model_dict` 都由 `returns` 派生，
  删除记录时同步回收该记录贡献的候选值与型号映射（后者仅在已无任何记录引用时才移除）。

| `SHIP_DETAIL_STATUS` | `{0:草稿, 1:开立, 2:核准中, 3:已核准}` | U9 出货单状态码 → 中文；同步时按它归一 |
| `SHIP_DETAIL_DEFAULT_STATUS` | `已核准` | 发货明细页默认只看已核准（草稿还没生效，混进来会虚高） |
| `SHIP_DETAIL_COLUMNS` | 14 列 | 发货明细的列定义（字段 / 表头 / 是否参与搜索），页面、接口、导出共用同一份 |
| `SHIP_DETAIL_STALE_HOURS` | `72` | 超过这个小时数没同步，状态卡标「已超期」 |
| `SHIP_DETAIL_EXPORT_LIMIT` | `200000` | 单次导出最多多少行；超出截断并在响应头 `X-Truncated: 1` 标出 |
| `ARS_ERP_HOST` / `_PORT` / `_DB` / `_USER` / `_PASSWORD` | 无默认 | ERP 连接；**没有默认密码**，缺了明确报错。也可在页面上填（存 `auth_db.setting`） |
| `ARS_ERP_INTERVAL_HOURS` | `12` | 物料主档自动同步间隔；页面配置可覆盖 |
| `BACKUP_STALE_HOURS` | `30` | 超过这个小时数没有成功备份，「数据备份」卡片标「已超期」 |

ARS_HOST=0.0.0.0                    # 允许局域网/公网访问

**上线前必做**：改掉初始管理员密码。首次登录会强制改密 ——

所以拿默认密码登录的人**无法**绕过这一步继续用系统。
但不要把这个环节拖到公网开放之后。

### 局域网开放访问（Windows 防火墙放行）

`start.bat --lan` 只把服务**绑到 `0.0.0.0`**（主界面 8000；数据接口 8100 仍留在
`127.0.0.1`，这是有意的）。同事能不能打开，还取决于防火墙是否放行入站 8000。
这一步**不在应用里做**（服务不该自己去改防火墙），用现成的小工具：

```bat
tools\open_lan_firewall.bat            :: 放行入站 TCP 8000（需要管理员，脚本会自己提权）
tools\open_lan_firewall.bat /status    :: 只看状态，不做任何改动
tools\open_lan_firewall.bat /remove    :: 收回放行
```

规则名固定为 `ARS main UI TCP 8000`（TCP / 入站 / 允许 / 三个 profile 都覆盖）。

**先判断到底要不要放行**（本机实测：Domain 开、Private 关、Public 开）：

```bat
netsh advfirewall show allprofiles state      :: 哪个档 ON 才会过滤（OFF 的档不过滤）
netsh advfirewall monitor show currentprofile :: 当前网卡实际套用的是哪个档
```

当前档若是 **Private 且状态 OFF**，不放行也能通；是 Domain/Public（我们这台就是
Public）就必须放行。等价的手工命令（管理员 CMD）：

```bat
netsh advfirewall firewall add rule name="ARS main UI TCP 8000" dir=in action=allow protocol=TCP localport=8000 profile=any
netsh advfirewall firewall delete rule name="ARS main UI TCP 8000"
```

Linux 侧不用这个脚本：

```bash
sudo ufw allow 8000/tcp                                                          # Debian / Ubuntu
sudo firewall-cmd --add-port=8000/tcp --permanent && sudo firewall-cmd --reload  # RHEL 系
```

**怎么算验证通过**：在**别的机器**上用浏览器打开 `http://<服务器局域网IP>:8000`。
本机访问自己的局域网 IP 会走回环，证明不了防火墙，务必换一台机器试。

**开放之后顺手检查三件事**：① 管理员密码已改（首次登录强制改，服务端也会拦）；
② 数据接口 8100 保持 `127.0.0.1`，`open_api_ips` 为空等于**不限制**，别把它一起开到
`0.0.0.0`；③ 测试账号 `smoke_runner` 在局域网里同样能登录，不用就禁用。

**收回**：`tools\open_lan_firewall.bat /remove`，再用不带 `--lan` 的方式重启
（`--local` 可强制回环）。

### 数据与备份

**业务数据在 MySQL 里**（六个 schema），项目目录下的 `data/` 只剩照片、备份与
各类状态文件。迁移时两样都要搬：

```
MySQL：returns_db  inspect_db  handle_db  delivery_db  items_db  auth_db
data/：photos/     backups/    *.json（同步状态、备份状态）     ← 随项目目录整体搬
```

> **数据库只管记录，照片是磁盘文件。** `data/photos/` 必须与库一起备份，
> 否则迁移后照片字段里的文件名会指向不存在的文件（缩略图位置显示破图）。
>
> **别直接拷 MySQL 的 datadir**：库文件在运行中始终处于「写了一半」的状态，
> 拷出来大概率是坏快照。用备份工具（下面）或 `mysqldump`。

**推荐用备份工具**（服务在跑也能做）：

```bash
python tools/backup.py                # 六库一致性快照 + 照片 + 轮转
python tools/backup.py --list         # 看现有备份（含「完整 / 不完整」）
python tools/backup.py --dry-run      # 只显示会做什么
python tools/backup.py --out /mnt/nas/ars   # 备份到异地
python tools/check_backup.py          # 校验最新备份 + **还原演练**
```

它调 `mysqldump --single-transaction`：在一个一致性读事务里导出全部六个 schema
（服务照常可写），产出 `data/backups/<时间戳>/all.sql` —— 纯文本 SQL，
配合 `photos/`、`MANIFEST.json`（大小 + sha256 + 逐表行数）和 `DONE` 标记，
**只有见到 `DONE` 才算可用**（定时任务失败是静默的，残缺备份不能冒充可用）。
轮转只删本工具产出的时间戳目录，人工建的 `backup_*` 快照不会被碰。

口令不进命令行：工具会写一份临时 `data/.backup_mysql.cnf`（权限 600）传给
`--defaults-extra-file`，跑完立刻删除。

**恢复**（演练与真恢复同一套动作，`tools/check_backup.py` 就是这么干的）：

```bash
# 1) 确认备份可用并做一次还原演练（会把 SQL 导进 verify_* 影子库比行数，跑完即删）
python tools/check_backup.py

# 2) 真恢复：库名改回真库再导入
sed 's/`verify_/`/g' data/backups/<时间戳>/all.sql > /tmp/restore.sql
mysql -u ars -p --default-character-set=utf8mb4 < /tmp/restore.sql

# 3) 照片
cp -a data/backups/<时间戳>/photos/. data/photos/
```

> 恢复前**先停服务**（`systemctl stop ars`），并且先留一份当前全量：
> `auth_db` 是唯一不可再生的库，恢复错了会影响登录。

定时执行：`deploy/ars-backup.timer`（systemd，每天 02:30，关机错过的会补跑）、
compose 里的 `backup` 服务、或宿主 cron —— 见 `deploy/README.md` 第七节。

**备份是否超期在界面上可见**：「权限设置 → 系统开关 → 数据备份」卡片显示
最近一次时间、距今小时数、大小与状态标签；超过 `BACKUP_STALE_HOURS`
（默认 30 小时）标「已超期」—— 把「备份悄悄停了」变成看得见的事。

### 并发与后续演进

MySQL 8 的 InnoDB：**读写并发、行级锁**。「登记」属低频写入
（一天几十到几百条），余量很大；并发瓶颈早已不在数据库这一侧。

引擎换代正是原先留的那条路：所有 SQL 都按「schema.表」前缀书写，业务层不感知
具体引擎 —— 2026-09-22 的 MySQL 改造就只动了 `core/db.py`（连接与 DDL）
和六处 `core/repo_*.py` 的方言，`app.py` 与前端**一行没改**。
这条经验保留下来：**写 SQL 时永远带上库前缀**，换引擎才是可控的。

## 登录验证与权限组

登录验证**默认开启**。未登录访问页面会被重定向到 `/login.html`，访问 `/api/*`
得到 401；无权操作返回 403。

### 权限模型：权限组 + 权限点

不是把角色写死在代码里，而是两层：

```
用户 ──属于──▶ 权限组 ──拥有──▶ 权限点（33 个）
```

权限点分三类：

| 类别 | 权限点 |
|---|---|
| 界面访问 `page.*` | 工作台 · 退回登记 · 检测登记 · 处理登记 · 明细查询 · 数据看板 · 匹配数据库 · **发货申请** · **待发货清单** · **发货跟踪** · **核销台账** · **发货明细** · **回收站** · 数据接口 · 权限设置 |
| 数据操作 `act.*` | 新增登记 · 修改明细与照片 · 删除明细 · 导出数据 · 物料维护 · **提交发货申请** · **修改发货申请** · **删除发货申请** · **登记发货 / 修改 / 撤销登记**（含导入与人工挂接；2026-09-21 起一个点覆盖发货记录的全部写操作） · **核销台账手工清账**（默认只给管理员） · **发货明细常规同步 / 连接配置**（增量，配置里带 ERP 账号密码；登记员也有） · **发货明细全量同步**（整表覆盖，**默认只给管理员**） · **匹配库同步 / 连接配置**（整表覆盖，会清空本地人工补的品名 / 旧料号 / 描述，**默认只给管理员**） |
| 系统管理 `act.*` | **回收站还原 / 彻底删除**（默认只给管理员） · 数据接口配置 · 用户与权限组管理 · 系统开关 |
> **权限一表全览**（2026-09-23 新增）：「权限设置 → 权限组」页签里多了一张矩阵表 ——
> **行 = 权限点、列 = 权限组**，一屏看清「哪个组缺哪一项」。原先按组编辑一次只能看到
> 一个组，比较两个组的差别要来回开弹窗、还得靠记。表左侧「权限点」一列与表头都吸附
> 固定（横向滚动时不会看丢是哪一行），权限点同时显示中文名与 `key`（排障时按 key 搜
> 代码/配置），最下一行是每组已授权的项数，与组卡片上的「N 项权限」对得上 —— 对不上
> 就说明权限点增删后页面没跟上。矩阵只读，改权限仍然走组的编辑弹窗（那里有服务端校验）。

预置三个内置组（不可删除）：

| 组 | 权限 |
|---|---|
| **管理员** | 全部 33 项。**权限不可修改、不可改名、不可删除**。它的权限会在每次启动时**强制同步为注册表里的全集** —— 否则新增权限点后，老库里的管理员组拿不到它，表现为「新功能的接口一律 403 而管理员不知道要去勾选」 |
| **登记员** | 日常登记与查询，含发货全流程（提交 / 修改 / 出队 / 登记 / 导入 / 挂接）与**发货明细的常规同步**（日常补数据要用），**不含删除发货申请、不含手工清账、不含发货明细全量同步、不含匹配库同步**（能看镜像，不能触发整表覆盖） |
| **只读** | 只能查看与导出（五个发货页都能打开，但不能提交 / 改 / 删 / 出队 / 清账 / 触发同步） |

> **老库里的内置组怎么拿到新权限点**：管理员组每次启动会**强制同步**为注册表全集
> （否则新增权限点后，老库里的管理员组拿不到它，表现为「新功能一律 403 而管理员
> 不知道要去勾选」）。登记员 / 只读这类**非锁定**内置组则**一字不改** —— 管理员
> 可能主动去掉过某项权限，自动加回来会违背「内置组可改权限」的约定。
> 所以 2026-09-22 给登记员补「常规同步」走的是 `core/auth.py` 的
> `BUILTIN_PERM_PATCHES`：一张**显式的定向补丁表**，只加不删、加过就不再动，
> 补了哪个组的哪个点、为什么补，都写在表里（新建库不依赖它，`PRESET_GROUPS`
> 已经是新权限）。

需要更细的岗位划分就新建自定义组，逐项勾选即可；内置组也能改权限
（管理员组除外）。

> **管理员组为什么锁死**：减掉它自己的权限、或把它删掉，系统里就再没有人能
> 改回来了 —— 一次误操作换来一个没有恢复入口的锁死状态。要限制某个人，
> 请把他放进别的权限组。同理，系统会拦住「停用 / 删除 / 改派最后一个管理员」。

### 实现要点

| 项 | 做法 |
|---|---|
| 密码 | 标准库 PBKDF2-HMAC-SHA256，12 万次迭代，`pbkdf2_sha256$iter$salt$hash`；不引入第三方依赖 |
| 会话 | 服务端记 `session` 表，Cookie 里只放随机 ID（HttpOnly + SameSite=Lax）；退出 / 停用 / 改密都能立即失效 |
| 拦截 | 一个中间件按顺序判三件事：未登录 → 页面权限 → 操作权限。**服务端独立校验，改前端代码绕不过去** |
| 前端 | 导航按权限过滤、顶栏显示当前用户与权限组、401 统一跳登录页（带 `?next=` 跳回）|
| 审计 | 登录成功 / 失败 / 退出 / 改密 / 用户与权限组变更 / 令牌与白名单变更，全部落 `auth_db.op_log` |

### 常用操作

| 想做什么 | 在哪做 |
|---|---|
| 加人 / 改权限组 / 重置密码 | 权限设置 → 用户管理 |
| 新建岗位权限 | 权限设置 → 权限组 → 新建权限组 |
| 关闭登录验证（本机单人用） | 权限设置 → 系统开关 |
| 改自己的密码 | 顶栏「改密」 |
| 看谁什么时候登录过 | 权限设置 → 审计日志 |

### 初始账号

首次启动且用户表为空时自动创建 **`admin`**，密码取自
`AUTH_BOOTSTRAP_PASSWORD`（默认 `admin123`），**首次登录强制改密**。

> 容器 / 服务器部署时可用 `ARS_BOOTSTRAP_PASSWORD` 注入自己的初始密码；
> 账号建好后把该环境变量删掉即可（只在用户表为空时才生效）。

## 数据接口（供外部系统定时拉取）

### 方向为什么反过来

原设计是**本系统主动往外推送**：要持有对端凭据、要维护推送队列、要处理冲突。
现在方向反过来，由**对端定时来拉**：

```
外部系统定时任务 ──HTTP──▶ 本系统开放接口（独立端口 8100）──▶ 返回 JSON / CSV / XLSX
```

好处是本系统不需要任何外部凭据、不需要出网，拉取节奏完全由对端控制。
代价是要把接口暴露出去 —— 所以「令牌 + 来源 IP 白名单 + 数据范围」
三件事都做成可配置项，且**默认只监听 127.0.0.1**。

### 端口划分

| 端口 | 服务 | 鉴权 | 面向 |
|---|---|---|---|
| `8000` | 主界面 + 业务接口 | 会话 Cookie + 登录 | 人 |
| `8100` | 数据开放接口 `/api/open/*` | 令牌 + 来源 IP 白名单 | 机器（外部系统定时任务）|

分开是为了让防火墙/安全组能只放行对外开放的那一个端口。

### 可用接口

| 接口 | 说明 |
|---|---|
| `GET /api/open/health` | 连通性探测，**免令牌**（只回服务名与版本，无业务数据）|
| `GET /api/open/ping` | 验证令牌是否有效 |
| `GET /api/open/datasets` | 可用数据集与字段清单（对端据此建表头）|
| `GET /api/open/data/{数据集}?since=&limit=&offset=` | 取数（JSON）|
| `GET /api/open/export/{数据集}.csv\|.xlsx?since=` | 导出文件（CSV 带 BOM，Excel 中文不乱码）|

### 数据集

| 键 | 内容 |
|---|---|
| `detail`（默认） | **明细汇总**：退回 + 检测 + 处理拼成一张平表，43 列 |
| `returns` | 仅退回侧字段 |
| `inspect` / `handle` | 仅检测 / 处理侧字段，按 `detail_key` 关联 |
| `items` | 物料主档全量 |

### 调用方式

```bash
# 连通性
curl http://<地址>:8100/api/open/health

# 增量拉取（since 传上次成功时间）
curl -H "Authorization: Bearer <令牌>" \
  "http://<地址>:8100/api/open/data/detail?since=2026-09-19%2012:00:00&limit=2000"
```

返回体里的 `next_offset` 不为 0 时带上它翻下一页；`rows` 为空即没有新数据。
建议对端把「本次成功时间」记在一个单元格里，下次作为 `since` 传回来 ——
即使中断几天，恢复后也能把漏掉的数据补齐。

### 三重鉴权

```
Authorization: Bearer <令牌>      ← 或 ?token= / X-API-Token
来源 IP 在白名单内                ← 留空 = 不限制；支持单 IP 与 CIDR
请求的数据集在授权范围内          ← 界面上勾选
```

任一项不过即拒绝，并记入拉取日志（界面上可查：谁、什么时候、拉了哪张表、
多少条、成功或拒绝）。

> **令牌只在「重置」时完整显示一次**，平时只保留掩码（`ars_yhA****L6s8`），
> 避免截图或投屏时整串外泄。接口本身也只返回掩码。
>
> **`X-Forwarded-For` 只在配置了 `TRUSTED_PROXIES` 后才被信任** ——
> 没配时只取传输层对端地址。这是刻意的：能被请求头伪造就等于白名单失效。

## 安全与健壮性（2026-09-20 自行审计）

一次针对性的自查，覆盖鉴权 / 权限 / 注入 / 路径 / 并发 / 信息泄漏。
结论与处置：

| 问题 | 原来 | 现在 |
|---|---|---|
| **页面路由路径遍历**（P1） | `GET /..%5C..%5Cfoo.html` 能读到 `static/` 之外的任意 `.html`（Windows 下 `\` 也是路径分隔符，而路由只挡 `/`）| `pages()` 加**页面名白名单**（字母/数字/下划线/连字符）；不要改回「过滤 `..`」的黑名单写法 |
| **非法字段名 500**（P1） | `GET /api/dict/<任意非字段名>` → 500 并把堆栈写进日志，谁都能刷 | 三个仓储模块统一抛 `InvalidField`，`app.py` 一个异常处理器转 **400** |
| **并发登记撞单号**（P1） | `next_order_no()` 只探测不占号，两人同时登记 → 5/8 失败，且报数据库英文原文 | 「取号 → 插入」放进同一临界区（`_ORDER_SEQ_LOCK`），外加跨进程重试；失败也转中文 |
| **拉取接口 `since` 静默出错**（P2） | 格式不对不报错：`not-a-date` → 0 条（**永久漏数据**）、`' OR 1=1 --` → 全量（**重复写入**）| `normalize_since()` 校验并规范化，非法格式 → **400** |
| **`/api/health` 泄漏部署信息**（P2） | 免登录白名单里的接口回带服务端绝对路径与各库文件位置 | 未登录只回 `{ok, time}`；已登录照旧回全量 |
| **弹窗未转义用户名**（P2） | `auth.html` 把用户名/组名直接拼进 `confirmDialog`（内部走 `innerHTML`）→ 用户名含 `<b>` 就能改变弹窗结构 | 补 `escapeHtml`，并加断言扫描全部调用点 |

**确认过没问题的**：SQL 注入（ORDER BY 与字段名全走白名单、其余参数化）、
鉴权覆盖（未登录页面 302 / 接口 401，只有 `/api/health` 与 `/static/` 免登录）、
越权（只读账号对 23 个写接口全部 403）、会话（每次登录换 sid、登出即失效、
SameSite=lax）、开放接口（令牌/scope/IP 白名单/导出格式/limit 上下界均正确）。

**已知取舍（非缺陷，供确认）**：

- 「只读」权限组默认带 `act.export`，也就是**只读账号可以导出全量数据**。
  如果客户的预期是「只读 = 只能看、不能导」，去权限设置页把这个权限点取消。
- 登录失败**没有次数限制**（内部工具够用；公网部署建议在反代层加限流）。
- 写操作**不校验 Origin/Referer**，目前靠 Cookie 的 `SameSite=lax` 挡跨站（够用，
  但如果哪天把 SameSite 改成 `None` 就必须补 CSRF 令牌）。

> 这几条都固化成了断言（后端 20 项 + 静态 7 项），改动会被立刻挡住。
> 静态断言写过一次假绿（`includes` 命中了注释），所以每条守卫断言都做过
> **负向测试** —— 故意破坏实现，确认断言真的变红。

## 常见问题

| 现象 | 处理 |
|---|---|
| 局域网同事打不开 | 默认本机模式，用 `start.bat --lan` 启动（或设 `ARS_HOST=0.0.0.0`）；再检查防火墙入站规则（Windows 跑一次 `tools\open_lan_firewall.bat`；先看 `netsh advfirewall monitor show currentprofile` 是哪个档，Private 且 OFF 就不用放行）|
| 一直跳登录页 | 登录验证已开启，用你的账号登录 |
| 忘了登录密码 | `python tools\reset_admin_password.py --user admin --random`（只改密码，不动其它账号与权限组）；**不要**直接 `DROP DATABASE auth_db`，那会连用户、权限组、审计日志一起丢 |
| 数据库连不上 / 数据库重启过 | 应用会**自己重连**：`core/dbapi.py` 在两个「连接断了」的报法上都重连一次再重试 —— `OperationalError`(2006/2013) 与 `InterfaceError(0, '')`（套接字死透时报的是后者，只认前者会一直 500 到人工重启）。所以 MySQL 重启不必重启应用；若界面持续 500，先 `python tools/dev_mysql.py status`（本机装的那份）或 `mysqladmin -h <host> -u ars -p ping` 看服务在不在，不在就 `python tools/dev_mysql.py start`。连接参数优先级：`ARS_MYSQL_*` 环境变量 > `data/mysql.json` > 内置默认 |
| 对端定时任务连不上 | 数据接口默认只监听 127.0.0.1，需设 `ARS_OPEN_API_HOST=0.0.0.0` 并放行 8100；先用 `/api/open/health` 测通 |
| 对端返回「未授权」 | 到「数据接口」页确认：令牌是否一致、来源 IP 是否在白名单内、该数据集是否已勾选授权 |
| 摄像头无法启用 | 需 `127.0.0.1` 或 HTTPS 访问；否则用扫码枪 |
| 扫码枪无反应 | 确认页面为当前活动窗口；扫码枪需为「键盘模拟」模式且以回车结尾 |
| 端口被占用 | `python app.py 127.0.0.1 8080` 换端口（或设 `ARS_PORT`）|
| **改了代码但界面看不到变化** | **分两类，先分清是哪一类**：<br>① **后端（`.py` / 配置）** —— Python 代码在**进程内存**里，改完**必须重启服务**（停掉旧进程再 `start.bat`）。这是最容易踩的：静态文件每次都读盘（是新的），`.py` 却还是旧的，于是出现「接口返回 404、界面少了入口」这种**半新半旧**的怪状态。<br>② **前端（HTML / CSS / JS）** —— 已用 `?v=` 版本号 + `Cache-Control: no-cache` 兜底，正常刷新即可；若仍旧，`Ctrl+F5` 强刷。<br>**自查命令**：用你的浏览器登录后访问 `/api/auth/me`，`perms` 应有 **28** 项；若比它少，就是服务进程还是旧的，重启即可 |
| 想重置数据 | **先备份**（`python tools\backup.py`），再 `DROP DATABASE` 掉六个 schema 重新启动（表结构启动时自动重建）；`data/photos/` 是文件，要单独清 |
| 从旧版单库升级 | `python tools\migrate_to_multidb.py`（SQLite 时代脚本，迁移前自动备份）；从 SQLite 整体搬到 MySQL 用 `python tools\migrate_sqlite_to_mysql.py` |
